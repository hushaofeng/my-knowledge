# 《AI Agent 实战》第十章：多Agent协作 - 核心知识笔记

---

## 一、多Agent协作的意义

### 1.1 突破单Agent能力边界
- 单个Agent受限于**模型能力边界**和**上下文窗口**
- 让多个Agent协同工作，不仅是"取长补短"，更根本的是：**群体智能可以高于个体**

### 1.2 通向超级智能的路径
- Google DeepMind将"大规模多Agent集体"列为从AGI通向ASI的关键路径
- 众多AGI级Agent协同形成的"群体智能"，可能表现出远超成员简单相加的认知能力

---

## 二、多Agent协作的分类框架

### 2.1 维度一：上下文是否共享

#### 共享上下文
- 后一个Agent接收前一个Agent的**完整对话历史和轨迹**
- 每个阶段切换系统提示词和工具集后变成新Agent
- **优势**：信息零损耗，每个Agent都能回顾之前任何阶段的细节
- **挑战**：上下文可能快速膨胀

#### 不共享上下文
- 每个Agent维护完全独立的上下文和对话历史
- 彼此无法直接访问对方的"思考过程"
- **优势**：模块化和隔离性更好，系统更易扩展和维护
- **代价**：必须通过显式通信机制传递信息

#### 三种通信机制（对应IPC两大范式）
| 机制 | IPC对应 | 特点 |
|------|---------|------|
| 工具调用参数 | 消息传递 | 适合类型确定、结构清晰的场景 |
| 共享文件系统 | 共享内存 | 适合产物较大或需持久化的场景 |
| 消息总线 | 消息传递（异步） | 适合多Agent并行协调场景 |

#### 选择依据（表10-1）
| 依据 | 共享上下文 | 不共享上下文 |
|------|-----------|-------------|
| 子任务数量 | 少（2-3个角色） | 多（需要并行处理） |
| 上下文窗口 | 足以容纳 | 单窗口装不下 |
| 并行度 | 串行为主 | 可大规模并行 |
| 信息隔离 | 不需要 | 需要 |
| 成本预算 | 单条轨迹接力 | 总token高出数倍到一数量级 |

**简单判断**：若累计上下文超过窗口50%，应不共享；若信息零损耗是硬约束，应共享

### 2.2 维度二：协作拓扑

三种典型形态（按复杂度递增）：

1. **对等协作模式**：2-3个Agent以平等身份交互，形成迭代改进循环
2. **管理者模式**：中心化Manager负责规划和调度，多个子Agent各司其职
3. **去中心化模式**：无中心控制者，Agent之间对等沟通协作

## 三、多Agent何时真正优于单Agent

### 3.1 核心判据
**协作过程是否引入了单个Agent在生成时无法获得的新信息？**

| 协作模式 | 是否引入新信息 | 效果 |
|---------|--------------|------|
| 同一模型自我审查 | 否 | 通常无效甚至有害 |
| 不同Agent辩论同一段文本 | 否 | 等计算量下与单Agent持平 |
| Reviewer使用测试执行结果审查代码 | 是（执行反馈） | 显著提升 |
| Reviewer查看渲染截图审查前端/PPT代码 | 是（视觉反馈） | 显著提升 |
| Reviewer使用外部工具验证事实 | 是（工具反馈） | 显著提升 |

### 3.2 关键研究发现
- **RLEF（2025）**：通过强化学习训练模型利用代码执行反馈迭代改进，效果远超独立多次采样
- **WebGen-Agent（2025）**：通过视觉反馈脚手架，Claude 3.5 Sonnet表现从26.4%提升到51.9%

### 3.3 步骤预算与Agent性能
- 单纯增加步骤数**不能保证性能提升**
- Agent需要**预算感知机制**：根据剩余资源动态调整策略
- BAVT（2026）：步骤级别价值评估，随预算减少从"广撒网"切换到"深挖掘"

### 3.4 成本考量
- 多Agent的token消耗约为普通对话的15倍
- 效果收益必须足够大，覆盖额外开销

## 四、共享上下文的多Agent协作

### 4.1 多阶段角色转换
- 根据当前阶段**动态切换系统提示词和工具集**
- 虽然角色切换，但对话历史和任务状态始终连续共享

**典型案例（实验10-1）**：
- 第一阶段：需求分析师 → 提问澄清，不写代码
- 第二阶段：软件工程师 → 基于需求编写代码
- 第三阶段：代码审查员 → 多维度评估代码质量

### 4.2 跨领域角色转换（实验10-2）
- **transfer_to_agent机制**：动态切换角色，保留完整对话历史
- 角色类型：triage（分诊）、research（检索）、coding（编程）、data_analysis（数据分析）、writing（写作）
- 路由规则在系统提示词中明确定义

## 五、不共享上下文的多Agent协作

### 5.1 与操作系统的对应关系（表10-3）

| 操作系统 | 多Agent系统 |
|---------|------------|
| 程序（可执行文件） | 静态前缀（系统提示词+工具定义） |
| 进程的内存 | 轨迹 |
| CPU | LLM |
| 内核 | Agent运行时 |
| 系统调用 | 工具调用 |
| fork | spawn_subagent |
| kill | cancel_subagent |
| ps | list_agents |
| 退出码与wait() | 子Agent返回的结构化摘要 |
| 共享内存/消息传递 | 共享文件系统/消息 |

**核心结论**：轨迹即Agent的全部状态，持久化轨迹可恢复会话

### 5.2 Agent虚拟文件系统的四类区域（表10-4）

| 区域 | 可见性 | 生命周期 | 读写 | 并发控制 |
|------|-------|---------|------|---------|
| Agent专属工作区 | 仅该Agent | 随实例销毁 | 读写 | 不需要 |
| 多Agent共享空间 | 所有协作Agent+用户 | 随任务持续 | 读写 | 需要（乐观锁/worktree） |
| 外部挂载资源 | 视外部授权而定 | 由外部源决定 | 多为只读 | 由外部源负责 |
| 系统内置资源 | 所有Agent | 跨会话稳定 | 只读 | 不需要 |

### 5.3 Agent间的通信与控制

**四项核心能力**：

1. **消息传递**：点对点或经消息总线，携带结构化信封（发送者、目标、类型、负载）
2. **状态查询**：
   - 消息传递方式：异步问答或主动汇报
   - 共享文件系统方式：轨迹持久化或约定进度文件
3. **执行终止**：
   - 优雅终止（graceful）：在安全点清理资源
   - 强制终止（forced）：直接终止进程
   - 级联终止：终止沿创建关系向下传递
4. **资源与调度**：token、资金、并发额度的分配

## 六、三种协作拓扑详解

### 6.1 对等协作模式

#### 提议者-审核者范式（核心）
- Proposer Agent负责生成，Reviewer Agent负责评估改进
- **关键设计原理**：审查的价值在于引入外部反馈，而非"让模型再想一遍"

#### Loop工程
- 循环的瓶颈在验证器，不在模型
- 由验证器而非模型自己判定"是否真的可以停"

#### 过早终止的三种形态
1. **偷懒式假完成**：只做一部分就宣称全部做完
2. **过早放弃**：一条路走不通就宣布整件事办不成
3. **假成功**：以为办成了，实际闭环没走完

**解法**：验证器+循环设计

#### 扩展模式
- **Debate（辩论）**：对抗性对话深入探索问题空间
- **Brainstorm（头脑风暴）**：相互启发探索解空间
- **Panel Discussion（专家小组）**：互补关系拼出问题全貌

### 6.2 管理者模式

#### 核心思想
- Manager Agent = 项目经理
- 把每个专门Agent建模为Manager可调用的工具
- 子Agent返回**结构化摘要而非全量轨迹**

#### 关键发现（Plan-and-Act 2025）
- **弱规划者是整个系统最关键的瓶颈**
- 应将最强模型和最精心设计的提示词分配给Manager

#### 顺序协调形态（实验10-3：书籍翻译Agent）
- Glossary Agent → Translation Agent → Proofreading Agent
- Manager只维护文件索引，不保存完整翻译内容
- 关键优势：**上下文隔离**，每个Agent在精简上下文中工作

#### 并行协调形态（实验10-4/10-5/10-6）
- 多个Agent同时工作，通过**消息总线**异步通信
- 实时监控、级联终止、竞态条件处理
- 典型场景：电话+电脑双Agent、多网站并行搜索

### 6.3 去中心化模式

#### 核心特点
- 没有单一中心控制者
- Agent之间以对等方式协作
- 移交包包含：任务描述、已确认的事实与约束、结构化产物的引用

#### 三种案例（由伪到真）

1. **MetaGPT**：SOP驱动的流水线
   - 共享消息池+按角色订阅
   - 控制流实际是固定的（伪去中心化）

2. **AutoGen group chat**：共享对话记录+中心化调度
   - 发言者选择器决定下一个发言者
   - 混合形态

3. **OpenAI Swarm/Agents SDK**：真正的对等移交
   - 每个Agent配备handoff选项
   - 控制权像接力棒流转
   - 风险：成环（需要移交次数上限保护）

## 七、跨组织协作：A2A协议

### 7.1 核心要素

1. **Agent Card**：描述Agent能力的元数据文档（"名片"）
2. **任务生命周期管理**：状态机（已提交→进行中→需要输入→已完成→失败）
3. **不透明协作**：只交换任务与产物，不暴露内部实现

### 7.2 与MCP的关系
- MCP：Agent与工具之间的互操作
- A2A：Agent与Agent之间的互操作（跨信任边界）

## 八、多Agent协作的失败模式

### 8.1 MAST分类法（14种失败模式）

**三大类**：
1. **系统设计缺陷**：接口定义不清、角色职责重叠、工具配置错误
2. **Agent间对齐失败**：任务目标理解不一致、信息被误解、操作相互矛盾
3. **任务验证缺失**：缺乏机制确认任务是否真正完成

**关键洞察**：Agent的故障是**拜占庭式的**——继续给出错误结论，错误不会主动声明

### 8.2 失败模式一：共享文件系统的并发冲突

**简单冲突（文件级）**：
- 两个Agent同时修改同一文件，后者覆盖前者
- 解决方案：**乐观锁**（版本号检查）

**语义冲突（跨文件）**：
- 文件层面无冲突，但逻辑上相互矛盾
- 解决方案：更高层语义校验、工作副本隔离

### 8.3 失败模式二：错误的级联放大

**特点**：
- Agent间传递语义，每次转述都是有损的重新编码
- 一个错误被后续Agent逐层强化

**解决方案**：**交叉验证**
- 让某个Agent以独立视角重新审视结论
- 不看前序Agent的思考过程，只看原始证据和最终结论

### 8.4 循环失控的三种失败
1. **token成本失控**：循环无人值守跑数小时
2. **理解债**：工程师对系统实现的理解越来越落后
3. **认知投降**：设计者习惯循环代劳，放弃独立思考

## 九、Agent社会与经济（前沿探索）

### 9.1 社交涌现

#### 斯坦福AI小镇（2023）
- 25个Agent在Smallville虚拟小镇自主生活
- **三大核心组件**：
  - 记忆流：完整经验记录流
  - 反思机制：定期回顾，把具体事件升华为概括认识
  - 计划与行动：目标导向+灵活调整
- **涌现行为**：自发组织情人节派对、竞选消息扩散、关系记忆、协调赴约

#### Agentopia（2026）
- 100个Agent连续模拟10年
- **设计亮点**：
  - 周制模拟流程
  - 文件式长期记忆
  - 生活奖励（社会地位、主观满足、经济收益）
- **关键成果**：模拟轨迹微调模型，"社会智慧"迁移到下游任务

#### Moltbook（2026）
- 150万Agent的社交网络
- **涌现现象**：自发创建数字宗教、机器原生协作协议

### 9.2 经济涌现

#### Vending-Bench Arena
- 多Agent在同一市场经营售货机竞争
- 涌现行为：价格战、价格同盟合谋

#### Agent经济平台
- **Pinchwork**：Agent-to-Agent任务市集，市场化雇佣
- **RentAHuman**：Agent用加密货币雇佣人类执行物理任务

### 9.3 策略博弈

#### 狼人杀实验（实验10-8）
- 核心机制：**信息不对称**
- 法官+信息权限控制的中心化设计
- 考验Agent的推理、伪装、识破伪装能力

## 十、核心设计原则总结

### 10.1 架构选型检查表
1. 子任务数量、上下文窗口、并行度、信息隔离、成本预算
2. 是否需要引入新信息（外部反馈）
3. 规划者能力是否匹配任务复杂度

### 10.2 关键设计要点
1. 子Agent返回结构化摘要，不是全量轨迹
2. 用验证器而非模型自己判定任务完成
3. 轨迹持久化支持会话恢复和审计
4. 消息总线支持异步并行协调
5. 乐观锁/工作副本隔离处理并发冲突
6. 交叉验证打断错误放大链

### 10.3 经典对应关系
- Agent ≈ 进程
- 轨迹 ≈ 内存
- LLM ≈ CPU（分时复用）
- 静态前缀 ≈ 程序
