# 《AI Agent 实战》Chapter 2 核心知识点提炼

## 第二章：上下文工程

---

## 一、核心概念：上下文决定能力上限

### 1.1 什么是上下文
- **定义**：每次与 AI 对话时，AI 实际"看到"的全部信息
- **组成部分**：
  - 对话历史
  - 系统指令（System Prompt）
  - 工具描述（Tool Definitions）
  - 其他元信息

### 1.2 核心观点
> **"上下文的质量才是 Agent 能力的真正上限"**

- 模型本身的智力只是基础
- 中等能力模型 + 精心组织的上下文 > 顶级模型 + 信息匮乏
- 决定 Agent 能力上限的不是模型参数量，而是每个决策点能获得多少、多精准的上下文

### 1.3 上下文工程的双重属性
- **技术问题**：如何组织和管理信息
- **组织问题**：团队的文档化程度决定 Agent 能发挥的效力

## 二、API 消息结构：理解上下文的技术基础

### 2.1 消息的四种角色

| 角色 | 含义 | 来源 |
|------|------|------|
| `system` | 系统提示词 | 开发者编写，最高优先级 |
| `user` | 用户消息 | 终端用户输入 |
| `assistant` | 助手消息 | 模型生成（文本回复或工具调用） |
| `tool` | 工具结果 | Agent 框架执行工具后返回 |

### 2.2 Agent 核心循环（ReAct 循环）

```
请求 → 工具调用 → 执行 → 送回结果 → 再请求
```

**关键特性**：
- 每次 API 调用都是**无状态**的
- 所有模型需要的信息必须在消息列表中完整提供
- Agent 框架的核心工作：管理 messages 列表

### 2.3 上下文的静态与动态划分

```
┌─────────────────────────────────┐
│  静态前缀（缓存友好）            │
│  - System Prompt                │
│  - Tool Definitions             │
├─────────────────────────────────┤
│  动态轨迹（持续增长）            │
│  - User 消息                    │
│  - Assistant 回复               │
│  - Tool 执行结果                 │
└─────────────────────────────────┘
```

## 三、KV Cache：底层优化原理

### 3.1 什么是 KV Cache
- **作用**：缓存已处理 token 的 Key-Value 向量，避免重复计算
- **价值**：将计算量从 O(N²) 降低到 O(N)
- **约束**：前缀必须完全不变，任何改动都会导致缓存失效

### 3.2 核心结论（必须记住）

> **三条铁律**：
> 1. 系统提示词和工具定义一旦确定就不要改
> 2. 动态信息永远追加到末尾
> 3. 使用标准 API 格式，不要自行拼接消息

### 3.3 常见错误模式

| 错误模式 | 问题 |
|----------|------|
| 动态系统提示词（如嵌入时间戳） | 缓存完全失效 |
| 滑动窗口对话历史 | 破坏前缀一致性 + 丢失工具结果 |
| 文本格式化（自行拼接消息） | 偏离模型训练格式，削弱能力 |
| 工具定义动态排序 | 缓存失效 |

### 3.4 KV Cache vs Prompt Cache

| 层级 | 作用范围 | 经济影响 |
|------|----------|----------|
| KV Cache | 单次请求内 | 性能优化 |
| Prompt Cache | 跨请求 | 直接影响计费 |

## 四、提示工程：系统提示词设计

### 4.1 设计原则

**检验标准**：大模型是一位聪明的新员工，能力出众但对你的一无所知。如果读完系统提示词还不知道该怎么做，Agent 也一样不知道。

### 4.2 语气与风格
- 大写字母（如 "NEVER do X"）更能引起模型注意
- 但过度使用会导致效果稀释，保留给真正关键的约束

### 4.3 结构化提示
- **XML 标签**：层次化语义，机器可解析
- **Markdown**：保持可读性，轻量级组织

### 4.4 流程驱动 vs 规则堆砌

**流程驱动的优势**：
- 模型清楚知道当前处于哪个阶段
- 异常处理有据可依
- 避免"遍历所有规则寻找匹配"

### 4.5 业务规则细化

**核心观点**：
> 模型的优势在于遵循复杂指令和从长上下文中提取信息，但不应该在业务规则制定上被赋予过多自由裁量权。

**实践建议**：
- 产品经理负责规则设计
- 工程师负责规则编码
- 规则必须明确到可执行的程度

### 4.6 Few-shot 示例

**何时使用**：
- 输出难以用规则精确描述时
- 特定风格的文案、结构化格式、语气分寸

**最佳实践**：
- 2-3 个精选示例胜过 10 个相似示例
- 示例位置保持字节级稳定（缓存友好）

### 4.7 工具定义设计

**关键要素**：
- 使用边界（"NEVER invoke grep as a Bash command"）
- 具体示例
- 性能提示
- 工具间协作关系

## 五、提示注入攻防

### 5.1 什么是提示注入
- 攻击者通过外部内容将伪装成系统指令的文本混入上下文
- Agent 拥有工具调用能力，危害远超普通聊天机器人

### 5.2 上下文层防御策略

| 策略 | 方法 |
|------|------|
| 来源标记 | `<external_content source="webpage">...</external_content>` |
| 结构化角色 | 严格利用 Chat Template 的角色体系 |
| 输入清洗 | 过滤可疑模式（容易被绕过，仅作辅助） |

### 5.3 新注入面
- Agent Skills：第三方 Skill 内容以高执行倾向进入上下文
- Agent 状态栏：状态栏投毒风险

## 六、Agent Skills：动态提示词与按需加载

### 6.1 核心思想
> 不是把所有知识一次性塞给 Agent，而是让它按需加载

### 6.2 渐进式披露三层结构

| 层级 | 内容 | Token 量 |
|------|------|----------|
| 第一层 | 元数据（name + description） | 数百 token |
| 第二层 | 核心流程（SKILL.md） | 按需加载 |
| 第三层 | 细则（子文档） | 按需深入 |

### 6.3 三种实现方式对比

| 方式 | 优点 | 缺点 |
|------|------|------|
| 注入 system 消息 | 指令遵循效果最好 | 破坏 KV Cache |
| 作为普通文件读取 | 不破坏缓存 | 依赖模型的中间位置指令遵循能力 |
| **生产实现** | 元数据提前提供 + 完整内容按需加载 | 兼顾缓存和效果 |

### 6.4 Skill 描述的设计要点
- **必须包含反例**："Don't use when..."
- 缺少反例会导致路由准确率明显下降

## 七、Agent 状态栏：元信息增强

### 7.1 核心原理

> **上下文学习更像检索而非推理**

- 注意力擅长在已有内容中"查找"
- 不擅长主动"归纳统计"
- 状态栏：把分散的隐式状态提炼为显式知识

### 7.2 类比
- 系统提示词 = 员工手册（入职时发，不变）
- Agent 状态栏 = 实时仪表盘（随任务推进更新）

### 7.3 实现位置
- 作为 **user 角色**消息追加到上下文末尾
- 不修改 system 消息，保护 KV Cache

### 7.4 状态栏包含的信息

| 类型 | 示例 |
|------|------|
| 任务规划 | TODO 列表 |
| 侧信道信息 | 时间戳、地理位置 |
| 环境状态 | 工作目录、系统时间 |
| 可用能力清单 | Skills 元数据 |

### 7.5 状态更新的两种实现

| 实现方式 | 缓存代价 | 适用场景 |
|----------|----------|----------|
| 每轮替换 | 末尾缓存失效 | 轨迹较短或状态消息很大 |
| 持久追加 | 完全友好 | 状态更新频繁且轨迹很长 |

### 7.6 三条实践经验

1. **状态栏用代码维护，别用 LLM**
2. **删原文前，确认状态栏覆盖所有可能问题**
3. **把状态栏准确率当成生产指标盯住**

## 八、上下文压缩策略

### 8.1 压缩的双重动机

| 动机 | 说明 |
|------|------|
| 解决长度约束 | 窗口有限，token 成本 |
| 提升思考质量 | 总结后的知识比原始形式更易使用 |

### 8.2 上下文腐化（Context Rot）

> "装得下但找不到了"

- 无关内容占据上下文大头
- 决策质量悄然下降
- 比上下文溢出更隐蔽

### 8.3 压缩与 KV Cache 的关系

- 压缩发生在**两次 API 调用之间**
- System Prompt 和 Tool Definitions 永远不动
- 压缩对象是对话历史中的 tool results

### 8.4 六种压缩策略对比

| 策略 | Token 量 | 特点 |
|------|----------|------|
| 无压缩 | — | 溢出失败 |
| 个体摘要 | 276,608 | 信息碎片化 |
| 组合摘要 | 93,449 | 可能丢失末尾信息 |
| **上下文感知压缩** | 40,157 | 最佳性价比 |
| 带引用的上下文感知 | 222,992 | 提供溯源 |
| 自适应窗口化 | 174,601 | 前期保留完整信息 |

### 8.5 生产级分层压缩机制

1. **工具结果预算控制**：大输出存磁盘，只看摘要
2. **噪声直接删除**：不做摘要，直接移除
3. **API 层微压缩**：服务端移除指定内容
4. **归档式摘要**：保留对话逻辑脉络
5. **全量压缩**：最后手段，配备熔断器

### 8.6 压缩时必须保留的内容

- 架构决策和关键约束（不得摘要）
- 已修改的文件列表和关键变更记录
- 验证状态（pass/fail）
- 未解决的 TODO 和回滚笔记
- UUID、hash、IP、端口、URL、文件名等标识符

### 8.7 隔离优于压缩

> **子 Agent 上下文隔离**

- 把大体积中间信息隔离在子 Agent 上下文
- 主上下文只接收结论性摘要
- 用隔离代替压缩，从源头避免噪声

## 九、核心洞察与金句

### 9.1 关于上下文
> "人和模型一样，最重要的是 Context。" —— 翁家翌（OpenAI 研究员）

### 9.2 关于能力上限
> 一个中等能力的模型配上精心组织的上下文，往往能胜过一个顶级模型在信息匮乏下的盲目摸索。

### 9.3 关于文档化
> AI Agent 就像一个永远的新员工：给足背景信息，它能干得很好；什么都不告诉它，再聪明也是白搭。

### 9.4 关于状态栏
> 状态栏之所以有效，根子上是因为它给模型喂进了它自己想不出来的信息。

### 9.5 关于压缩
> 压缩即理解——不要让模型被动地在海量信息中检索，而要主动为模型提供经过提炼的结构化知识。

## 十、思考题要点

1. **滑动窗口 vs 完整历史** → 策略：分层保留 + 自适应压缩
2. **思维链保留策略** → DeepSeek R1 剥离 vs V4 强制回传，体现"思考是状态，不是废料"
3. **极端压缩风险** → 不可逆信息损失，需保留关键标识符 + 溯源引用
4. **状态栏可靠性** → 用代码维护 + 生产指标监控
5. **系统提示词熵增** → 版本控制 + 消融实验验证
6. **检索 vs 推理局限** → 需要新的架构突破（如交互缩放）
7. **Skills 元认知问题** → 需要模型知道"自己不知道什么"
8. **模型对 Skills 支持差异** → 训练数据差异导致
9. **工具集频繁变动** → 按需加载机制 + 固定元数据前缀

---

## 总结

本章核心：**给模型看什么、怎么组织，比模型本身有多聪明更影响最终结果**

技术链条：
```
API 消息结构 → KV Cache 约束 → 提示工程 → Skills 按需加载 → 状态栏注入 → 压缩策略
```

共同特点：**显式的、工程化的信息管理**

- 不要让模型被动寻找
- 主动提供经过提炼的结构化状态
- 用工程手段最大化信息利用效率
