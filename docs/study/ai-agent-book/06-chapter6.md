# 《AI Agent 实战》第六章：Agent 的评估 - 知识笔记

---

## 一、核心概念

### 1. 评估体系的核心定位
- **评估对象**：不应只是模型，而是**模型与 Harness 的组合体**
- **评估价值**：为设计决策提供科学依据，区分真正的能力提升与表面波动
- **核心功能**：在 Harness 中扮演"验证"功能的核心角色

### 2. 评估体系的三个层次

| 层次 | 核心问题 | 内容 |
|------|---------|------|
| 第一层：评估环境 | 在哪里测 | 搭建自动化、可复现的测试环境 |
| 第二层：评估方法 | 怎么判 | 数据集设计、指标体系、LLM-as-a-Judge |
| 第三层：评估驱动的决策 | 测了干什么 | 模型选型、架构优化、持续迭代 |

### 3. 评估环境的五种要素
1. **数据集（Dataset）**：任务集合，含初始状态、目标描述、参考方案
2. **环境状态（Environment State）**：任务执行中的可变信息
3. **工具接口（Tools）**：Agent 可执行的操作集合
4. **评分标准（Rubric）**：量化 Agent 表现的准则
5. **执行协议（Interaction Protocol）**：交互模式和终止条件

### 4. 两种核心评估范式

#### 工具调用型评估环境
- **Verifiers 框架层次化设计**：
  - `SingleTurnEnv`：单轮任务（无状态、无工具）
  - `ToolEnv`：多轮工具调用（无状态、多轮）
  - `StatefulToolEnv`：有状态工具调用（有状态、多轮）
  - `SandboxEnv`：沙盒环境（有状态+隔离、多轮）
- **验证方式**：基于可执行标准（测试通过、答案匹配）

#### 人机交互型评估环境
- **核心理念**：渐进式信息透露（Progressive Information Disclosure）
- **τ-bench 方案**：用户模拟（User Simulation）——用另一个 LLM 扮演用户
- **τ²-bench 增量**：
  - 双控环境：用户模拟器也能操作共享环境
  - 更精确的任务规范与组合式任务生成

### 5. 关键评估指标

#### Pass@k vs Pass^k vs Best@k
| 指标 | 定义 | 适用场景 |
|------|------|---------|
| Pass@k | k 次尝试中至少有一次成功 | 评估能力天花板（探索性任务） |
| Pass^k | k 次尝试全部成功 | 验证稳定性（回归测试） |
| Best@k | k 次尝试中最好的得分 | 开放任务的质量上限 |

### 6. LLM-as-a-Judge
- **定义**：让语言模型根据专家定义的评分标准（Rubric）进行评判
- **价值**：在自动化规模和人类专业判断之间取得平衡
- **已知局限**：
  - 长度偏差（倾向给更长的回答打高分）
  - 同源模型问题（Agent 可能学会利用评判模型偏好）

## 二、关键观点

### 1. 评估的首要价值
> **评估体系的首要价值不是给当前系统打分，而是让你能快速、可靠地跟上模型的演进。**

拥有完善评估体系的团队，当新模型发布时能在数小时内得出切换决策；缺乏评估体系的团队只能凭直觉或等待社区反馈。

### 2. 模型替换实验 vs 消融实验
| 方法 | 操作 | 目的 |
|------|------|------|
| 模型替换实验 | 固定 Harness，只换模型 | 区分瓶颈在模型还是 Harness |
| 消融实验 | 关闭 Harness 某个组件 | 定位 Harness 内部哪个部件重要 |

### 3. 数据集设计的五大挑战
1. **明确性与开放性的张力**
2. **真实性与可控性的平衡**
3. **多样性与系统性的协调**
4. **评估成本与覆盖范围**
5. **数据泄漏防范**

### 4. 数据泄漏防范策略
| 基准 | 防范策略 |
|------|---------|
| GAIA | 答案独特性 + 专门创建的附件文件 |
| SWE-bench-Live | 时间新鲜度（收录训练截止日期后的新 issue） |
| τ²-bench | 动态参数生成（每次随机生成具体实例） |
| AndroidWorld | 参数化任务生成 + 基于 UI 状态验证 |
| Terminal-Bench | 金丝雀标识符（canary GUID）使泄漏可检测 |

### 5. Rubric 四准则（Scale AI）
1. **基于专家指导**：必须反映领域知识，捕捉核心事实和推理步骤
2. **全面覆盖**：涵盖准确性、逻辑性、完整性、安全性，明确陷阱（Pitfall）
3. **标准重要性权重**：必要项、重要项、可选项、陷阱项；支持**一票否决机制**
4. **自包含评估**：每个评价项独立可操作，不依赖评价者的领域知识

### 6. 成本的三个层次
1. **模型推理成本**：输入/输出 token + 上下文累积效应 + 思考 token
2. **工具调用成本**：外部 API 费用 + 工具返回结果的 token 费用
3. **基础设施成本**：向量数据库、消息队列、日志存储等

### 7. 成本优化三大杠杆
- **KV Cache 复用**：可降低 30%-60% 的输入 token 成本
- **上下文压缩**：控制上下文增长速率
- **模型分层路由**：简单请求给轻量模型，复杂任务给强力模型

## 三、实践要点

### 1. Benchmark 报告分析流程
1. **诊断**：交叉分析逐任务表格和能力标签矩阵
2. **构建假设**：按三层框架（表层→中层→深层）
3. **分阶段实验**：验证假设，观察改进幅度和副作用
4. **数据驱动决策**：权衡成本收益比
5. **迭代**：改进后重新评估，新报告成为下一轮起点

### 2. 假设分层框架
| 层次 | 特点 | 示例 |
|------|------|------|
| 表层假设 | 成本低、可并行验证 | 增加导航提示、补充 UI 元素识别规则 |
| 中层假设 | 同样独立、可并行 | 修复多模态输入管道、启用思考模式 |
| 深层假设 | 验证成本高，条件化启动 | 更换视觉模型、增加 UI 元素树信息 |

### 3. 内部评估基础设施五大组件
1. **消融基础设施**：每个主要特性可独立关闭，定期验证实际贡献
2. **AB 测试方法论**：多臂设计、区分机制指标和目标指标、设置护栏指标
3. **双层特性开关系统**：编译时开关 + 运行时开关
4. **提示词敏感性评估**：可确定性渲染、版本化快照、回归测试
5. **隐私感知的分析**：类型系统强制隐私约束

### 4. 仿真环境设计要点
- **与评估环境的核心区别**：
  - 交互频率远高（数百万次 vs 数千次）
  - 需要随机化（防止死记硬背）
  - 必须提供即时反馈
- **两大要求**：
  - 可靠的 reset 语义
  - 远高于评估的吞吐
- **领域随机化**：缩小仿真与现实差距（sim-to-real gap）

## 四、扩展思考

### 1. 思考题精选

#### 数据泄漏的"猫鼠游戏"有终局吗？
- **现状**：公开 benchmark 数据很快被纳入训练数据
- **思考方向**：
  - 动态生成机制（参数化模板）
  - 时间新鲜度策略（持续收录新问题）
  - 金丝雀标识符使泄漏可追踪
- **根本矛盾**：评估需要公开，公开则可能泄漏

#### LLM-as-a-Judge 的系统性盲区
- **问题**：模型可能给某种风格打高分，与人类判断不一致
- **应对**：
  - 多源异构评判（使用不同模型家族）
  - 人工标注金标集校准
  - 定期审计评分与回答长度的相关性

#### 配对比较中的非传递性偏好
- **理论假设**：如果 A > B 且 B > C，则 A > C
- **现实挑战**：人类偏好经常违反传递性
- **影响场景**：
  - 不同任务类型间难以排序
  - 评分依赖具体问题分布

### 2. 方法论核心

> **观察 → 假设 → 实验 → 验证 → 新认识 → 新假设**

这是将 Agent 工程从经验驱动的"炼金术"转向数据驱动的科学工程的关键路径。

### 3. 评估闭环

```
评估环境 → 评估数据集 → 自动化评估方法 → Benchmark 分析 → 系统改进 → 更新评估环境
```

### 4. 与后续章节的联系
- **第七章**：把评估环境和数据转化为模型后训练的输入
- **第八章**：把生产轨迹的多维评价转化为可执行的系统更新

## 五、核心基准对比速查

| 基准 | 类型 | 核心特点 | 验证方式 |
|------|------|---------|---------|
| GAIA | 工具调用型 | 三级难度、通用性、附件文件 | 字符串精确匹配 |
| AndroidWorld | GUI 操作 | 116 任务/20 应用、参数化模板 | UI 状态验证 |
| SWE-Bench Verified | 代码生成 | 500 高质量任务、人工验证 | 测试通过/FAIL_TO_PASS |
| τ²-bench | 人机交互 | 渐进式信息透露、双控环境 | 数据库状态 + 对话内容 |
| Terminal-Bench | 终端操作 | 200+ 任务、跨技术栈 | 文件系统 + 程序执行 |
| OSWorld | OS 操作 | 跨三个操作系统、134 评估函数 | 文件系统 + DOM 树 + 后端验证 |
