# 《AI Agent 实战》第四章核心知识点

## 一、工具分类框架

### 五类工具总览

| 工具类型 | 调用方向 | 作用对象 |
|---------|---------|---------|
| 感知工具 | Agent 主动调用 | 获取信息 |
| 执行工具 | Agent 主动调用 | 改变世界 |
| 协作工具 | Agent 主动调用 | 驱动其他 Agent 或人类 |
| 用户沟通工具 | Agent 主动调用 | 向用户传递信息 |
| 事件触发工具 | Agent 注册、外部触发 | 驱动 Agent 开始执行 |

### 各类工具详解

**感知工具**：Agent获取外部信息的主要渠道
- 示例：web_search、knowledge_base_search、fetch_url、find_file、grep_file、read_file
- 核心：粒度权衡 + 输出信息量控制

**执行工具**：Agent改变外部世界的方式
- 示例：shell_exec、code_interpreter、write_file、edit_file、send_email
- 核心：错误代价高，安全约束是设计核心

**协作工具**：Agent与其他Agent及人类协作的方式
- 示例：spawn_subagent、send_message_to_subagent、cancel_subagent、list_agents
- 用途：并行执行、使用不同模型/工具/提示词执行不同任务

**用户沟通工具**：Agent主动向用户传递信息的方式
- 示例：reply_to_user、send_card_to_user、send_user_notification
- 背景：多渠道异步消息场景下，"说话"成为显式工具调用

**事件触发工具**：外部世界驱动Agent行动的方式
- 示例：set_timer、monitor_shell、connect_channel
- 关键：注册时Agent主动调用，触发时由外部事件异步回调

## 二、工具设计的通用原则

### 1. 能力表达形式选择

**专用代码工具** vs **Skill + 通用执行器**

| 形态 | 优点 | 缺点 |
|-----|------|------|
| 专用代码工具 | 结构化、可测试、确定性高 | 占token多，数量膨胀破坏KV Cache |
| Skill + 通用执行器 | 灵活、省token、覆盖场景广 | 依赖模型能力 |

**决策三维度**：
- 参数复杂度：复杂嵌套对象用专用工具，简单参数可用CLI
- 变更频率：频繁变化用Skill，稳定操作用专用工具
- 模型能力：SOTA模型可用Skill方式，弱模型需结构化schema引导

### 2. 工具粒度权衡

**整合标准**：功能相似性 + 使用场景重叠度

整合优势：
- 降低LLM认知负担
- 描述更清晰
- 便于扩展

整合边界：参数形态差异大、延迟特性不同、使用频率极高时保持独立

### 3. 工具通用性设计

**核心原则**：通用工具优于专用工具，除非存在明确的安全/权限/性能理由

示例：`code_interpreter` 比十几个专用计算器更省token、更灵活

**边界**：需要特殊权限、复杂配置、安全风险的操作需要专用工具

### 4. 工具描述的艺术

**核心**：让LLM知道"什么时候用"，而不只是"能做什么"

关键要素：
- 使用时机说明（如"当需要获取实时信息或查找未知事实时使用"）
- 边界条件（做不到什么、不接受什么输入）
- 参数描述用具体例子代替抽象规范
- 返回值结构说明
- 执行代价标注
- 1-5个真实调用示例（准确率可从72%提升到90%）

**调试原则**：Agent频繁选错工具时，优先检查工具描述而非怀疑模型能力

### 5. 参数传递的保真性

**红线**：模型感知的世界与工具操作的世界之间，不能存在系统性偏差

**反模式**：
- 静默输入转换（如Cursor弯引号转直引号导致匹配失败）
- 静默参数注入（如自动附加git commit参数导致报错）

**要求**：参数传递必须透明，必须修改时要在工具描述中说明

### 6. 工具设计演进三阶段

| 代际 | 特点 |
|-----|------|
| 第一代 | 直接API封装，粒度过细 |
| 第二代 | ACI原则：工具对应Agent目标而非底层API |
| 第三代 | 优化调用/串联/发现方式：示例驱动、动态发现、代码编排执行 |

## 三、工具生态：MCP协议

### MCP核心设计

**架构**：客户端-服务器架构
- MCP服务器：暴露一组工具
- MCP客户端（Agent框架/IDE）：通过标准化协议通信

**关键决策**：
1. 标准化工具描述格式（JSON Schema）
2. 传输层灵活：本地stdio / 远程Streamable HTTP
3. 原语分离：工具（执行）| 资源（只读）| 提示模板

### MCP的价值与局限

**价值**：一次开发，处处可用

**局限**：
- 请求-响应式，缺乏跨会话事件驱动标准
- 工具描述注入上下文开销大（5个服务器约55K token）

**缓解方案**：
- 文件系统作为上下文接口（默认只看工具名索引，按需查询定义）
- 总token消耗可减少46.9%

### MCP安全风险

| 风险类型 | 说明 | 缓解措施 |
|---------|------|---------|
| 工具描述投毒 | 恶意服务器在description中夹带指令 | 接入前审查工具描述 |
| 恶意/被劫持服务器 | 供应链攻击或服务器被入侵 | 锁定服务器版本 |
| 同名工具遮蔽 | 恶意服务器遮蔽正规工具 | 最小权限凭证配置 |
| 凭证管理风险 | Agent持有OAuth token/API key | 设置有效期，不复用高权限凭证 |

### 工具发现方法

1. **检索式预筛选**：按语义相似度一次性匹配（局限：无法预见后续步骤需求）
2. **主动声明发现**：Agent声明能力缺口，系统动态匹配注入（MCP-Zero）
3. **层次化匹配**：服务器级→工具级两层语义路由
4. **Skills渐进式披露**：Agent启动只看目录，按需查阅详细定义

## 四、感知工具设计要点

### 核心挑战
返回信息量远超Agent处理能力（数万字符搜索结果、上百页PDF）

### 解决方案

**上下文感知压缩**：输出超阈值（如10000字符）时，基于查询意图自动压缩

**搜索类工具**：
- 返回结构化候选列表（标题、位置、摘要）
- 支持分页/游标，默认返回前若干条

**读取类工具**：
- 支持offset/limit参数
- 截断时显式可见（注明省略内容和读取方式）

**只读性红利**：
- 结果可安全缓存
- 多个感知调用可并行执行

**多模态感知**：
- 纯文字用文本提取
- 布局敏感内容（UI、表格、设计稿）保留图像

## 五、执行工具安全机制

### 层次化安全防护体系

| 层级 | 机制 | 说明 |
|-----|------|------|
| 第一层 | 输入验证 | 检查路径遍历、命令注入、参数格式，快速失败 |
| 第二层 | 权限控制 | 工作目录限制、禁止命令黑名单、配额检查 |
| 第三层 | 智能审查 | 提议者-审核者机制、Sidecar机制 |

### 提议者-审核者机制

**事前审批**：
- 提议模型：行动导向，任务完成
- 审批模型：风险控制，规则遵守
- 模型选择：不同家族、相似能力水平（认知多样性）

**事后验证**：
- 模态切换检验结果（代码→渲染截图，配置→沙盒运行）

### Sidecar机制

**定义**：伴随主Agent思考循环运行的轻量级LLM调用，对工具调用做独立安全判断

**关键设计**：
- 只看结构化字段（工具名、参数），不看主模型自由文本
- 与主模型流式输出并行运行
- 亚秒级完成

**对比提议者-审核者**：

| 维度 | 提议者-审核者 | Sidecar |
|-----|--------------|---------|
| 执行时机 | 操作前/操作后 | 与流式输出并行 |
| 审查对象 | 操作合理性/结果 | 操作本身 |
| 输入隔离 | 提议者和审查者看相似信息 | 刻意隔离主模型自由文本 |

### 自动验证闭环

**原则**：如果操作结果可以被验证，就应该自动验证

示例：write_file后立即执行语法检查（linter），返回结构化错误列表

### 幂等性与取消语义

**幂等性**：同一操作执行一次和多次，影响完全相同

实现手段：
- 携带唯一标识（idempotency key）
- 先查询后变更

**不可幂等操作**（发送邮件、转账）：采用"预检-确认"两段式

### 执行环境隔离

| 隔离层级 | 机制 | 特点 |
|---------|------|------|
| OS级 | sandbox-exec、seccomp | 轻量本地方案 |
| 容器 | Docker | 独立文件系统/网络栈，共享内核 |
| microVM/虚拟机 | Firecracker | 独立内核，硬件级隔离 |

**注意**：Python venv不是沙盒，只隔离包依赖

## 六、协作工具设计

### 子Agent设计哲学

**核心价值**：专业化分工——各子Agent独立优化提示词、工具集、知识库

### 子Agent提示词关键要素

1. **角色定义清晰**："你是专门负责XXX的助手Agent"
2. **上下文来源标注**：`[FROM_MAIN_AGENT]`、`[FROM_USER]`、`[TOOL_RESULT]`
3. **任务边界界定**：职责范围内/外
4. **输出格式标准化**：统一JSON结构

### 协作工具三组原语

| 原语组 | 工具 | 说明 |
|-------|------|------|
| 启动与取消 | spawn_subagent, cancel_subagent | 创建/终止子Agent |
| 消息传递 | send_message_to_subagent | 双向通信 |
| 发现 | list_agents | 列出可用Agent及状态 |

### 人工介入（HITL）

**超时降级策略**：
- 设置超时阈值和默认行为
- 优先级队列（紧急多渠道，普通仅邮件）

**反馈循环**：人类批准/拒绝及理由构成反馈数据，进入经验知识或后训练数据

## 七、事件驱动的异步Agent架构

### 为什么需要异步

**同步Agent局限**：
- 要么等待后台任务完成才能对话
- 要么等对话结束才能处理新事件

**异步需求**：
- 异步执行是常态（长时间任务不阻塞交互）
- 事件优先级动态判断
- 中断和恢复流畅性

**根本矛盾**：LLM训练范式假设同步（发出工具调用后，下一条消息必须是工具结果），但真实部署要求异步

### 事件触发工具三类

1. **定时器**（set_timer）：处理依赖物理时间的事件
   - 一次性定时器：明确时间点任务
   - 循环定时器：周期性任务

2. **后台任务监控**（monitor_shell）：监控长时间命令行任务

3. **外部事件通道**（connect_channel）：实时推送新邮件、API回调、IM消息

### 用户沟通工具

**范式转变**：从原生ReAct（assistant消息直接发给用户）到专用工具发送消息

**设计要点**：
- 支持异步消息模式
- 多渠道选择（IM、短信、邮件、电话）
- 消息一致性保持

### 虚拟身份与隔离执行环境

**架构选择**：Agent应拥有独立虚拟身份（专属通讯账号、存储、计算环境）

**优势**：
- 操作可追溯、可审计
- 错误不影响宿主系统

**挑战**：
- 反自动化机制（CAPTCHA、IP信誉检测）
- 需要用户真实账号场景：Human-in-the-Loop认证

### 事件处理机制

**事件循环核心**：事件只在每轮循环的边界被消费

**事件结构化建模**：
- 来源（谁）：用户/联系人/陌生人/系统
- 渠道（方式）：电话/短信/IM/邮件/定时器
- 内容（什么）：文本/情感/紧急度
- 上下文（背景）：对话关联/任务关联

### 三种事件处理策略

| 策略 | 适用场景 | 机制 |
|-----|---------|------|
| 取消式处理 | 紧急事件（用户中断、监督指令） | 主动制造安全点，清空队列，重新调用LLM |
| 队列式处理 | 常规事件（工具结果、补充信息） | 等待当前操作完成，批量追加到轨迹 |
| 并行处理 | 独立轻量级查询（如天气查询） | 另起推理会话独立执行 |

### 工程权宜：模拟同步的异步实现

**五条规则**：

| 规则 | 内容 |
|-----|------|
| 规则1 | LLM输出时立即记录assistant message |
| 规则2 | 工具调用完成时才记录tool result |
| 规则3 | 工具执行中的打断需要占位符 |
| 规则4 | LLM思考中的打断直接丢弃当前思考 |
| 规则5 | 非打断事件进入队列等待批处理 |

**核心优势**：常态下LLM看到完美的同步轨迹

**风险**：占位符可能加剧幻觉

### 异步工具接口设计

**原则**：从"调用即完成"到"启动与完成解耦"

示例：
- `initiate_phone_call`：启动呼叫，立即返回任务ID
- 通话进展通过事件通知

### 未来方向：模型进化

**异步RL训练需要三种核心能力**：
1. 理解轨迹中事件的异步穿插
2. 恢复被打断的任务和思考
3. 批量事件的综合处理

**持续思考模式**：用约两百行编排逻辑，让现成文本思考模型变成持续思考Agent

## 八、主动工具发现

### 现有方法对比

| 方法 | 说明 | 局限 |
|-----|------|------|
| 全量注入 | 所有工具schema一次性注入 | 工具上千时失效 |
| 检索预筛选 | 按语义相似度一次性匹配 | 无法预见后续步骤需求 |
| 主动声明发现 | Agent声明能力缺口，系统动态注入 | 需嵌入索引基础设施 |
| Skills渐进式披露 | 启动只看目录，按需查阅 | - |

### 层次化匹配

服务器级→工具级两层语义搜索：
- 先按能力描述定位相关服务器
- 再在服务器内匹配具体工具
- 候选相似度低于阈值时返回"未找到"

### 动态加载与KV Cache

**关键**：动态加载工具会破坏KV Cache

**解决**：
- 新工具schema追加到上下文末尾
- 静态前缀保持稳定，KV Cache复用
- 主流API原生支持：OpenAI Responses API、Claude Code

### Skills：按需查阅范式

**特点**：
- Agent启动只看目录（name + description，数百token）
- 按需读取sub-skill，顺着引用继续查阅
- 不需要嵌入索引，用通用文件阅读能力

**KV Cache优化**：skill的KV表示预编译并缓存，用RoPE重定位"粘贴"到任意位置

## 十、核心结论

1. **工具设计质量决定Agent能力上限**，异步架构决定Agent能否可靠运行

2. **ACI原则**：工具应对应Agent目标而非底层API

3. **参数传递保真性**是贯穿所有工具设计的底线

4. **执行工具安全**需多层层防护：输入验证→权限控制→智能审查

5. **异步与同步矛盾**：当前只能用工程手段缓解，根本解法需模型训练范式转变

6. **工具发现**：Skills渐进式披露是更轻量、更现代的思路
