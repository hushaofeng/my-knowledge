# 02 · 漏洞研究方向——从使用者到发现者

> 前两年你是漏洞的"使用者"；这个方向让你成为"发现者"。核心竞争力：源码/补丁的**深度阅读**——这恰是资深工程师的舒适区。

## 🎯 学习目标

1. 建立 CVE 复现的工程化模板（容器化+报告化）
2. 掌握补丁 diff 分析法
3. 跑通一次 Fuzzing 最小闭环
4. 说清负责任披露（CVD）流程

## 📖 核心知识

### 2.1 CVE 复现工程化（你的第一个复现库）

```
cve-lab/
├── CVE-2021-44228-Log4Shell/
│   ├── docker-compose.yml     # 漏洞环境一键起
│   ├── poc.py                 # 参数化 PoC（第 1 年 04 的规范）
│   ├── README.md              # 漏洞原理/影响版本/复现步骤/修复分析
│   └── notes.md               # 调试过程（失败了什么、为什么）
```

复现是"最便宜的漏洞研究教育"：每个 CVE 教你一个"新的代码模式如何变危险"。目标节奏：2 周 1 个 → 年底 25 个入库（每篇复现=一篇博客，你的知识库直接滚动增长）。

### 2.2 补丁 diff 分析法（系统化）

```
1. 来源：GitHub Advisory / 厂商公告 / NVD
2. 拿到 fix commit → 只看三类变更：
   a) 新增校验/过滤 → 原缺陷类型（说明当初信任了什么）
   b) 类型/解析方式变更（String→URI）→ 原解析被滥用
   c) 依赖升级 → 传递漏洞
3. 反推 PoC：变更语义 = "原来允许 X，现在不允许" → 构造 X
4. 检查同类代码：grep 同模式 → 疑似同族漏洞（1-day 逻辑的捷径）
```

实例思维：某 SSRF 修复把 `new URL(input)` 换成了白名单校验 → 反推原版本信任完整 URL → 测试 DNS rebinding/重定向绕过历史缺口。

### 2.3 Fuzzing 入门（AFL 最小闭环）

原理：覆盖率导向变异——记录输入覆盖了哪些分支，**优先变异"走得最远"的输入**。

```
目标：一个解析输入文件的程序（如 图片/配置 解析器）
1. 用 afl-gcc/afl-clang-fast 重编译目标（插桩）
2. 准备种子语料（正常样例文件）
3. afl-fuzz -i seeds -o out ./target @@
4. 看 crashes/ 目录 → 每个崩溃样本 → gdb 定位 → 判定可利用性
```

认知要点：Fuzzing 强在"找内存破坏与解析缺陷"，弱在"逻辑漏洞"（它不懂业务）。工程时间分配：Fuzzing 后台跑，人工 diff 分析前台做。

### 2.4 从研究到披露（CVD 负责任流程）

```
发现问题 → 本地确认可复现 → 判断影响与可利用性
→ 联系厂商（安全邮箱/PSIRT）→ 给出 90 天修复窗口
→ 厂商修复发版 → CVE 编号申请（MITRE/厂商 CNA）
→ 协调发布：报告+补丁同日公开
```

红线：**未协调公开 = 可能违法（提供侵入工具/破坏秩序）**；细节在补丁发布前不披露、不留底、不分享。

### 2.5 目标产出（第 3 年）

- 1 个 CVE 编号 或 1 篇高质量漏洞分析（先知社区/个人博客）
- 25+ 复现库（GitHub 展示=简历硬资产）
- 1 个 Fuzzing 产出（crash 分析报告）

## 🔬 动手实操

选一个"修复已完整披露"的经典 CVE（如 Fastjson/Log4j 系）按 2.1 模板完成复现全流程：环境→PoC→修复 diff 分析→博客。

## ⚠️ 常见坑

1. 只复现不复现"为什么"——原理笔记才是资产
2. Fuzzing 无种子工程——种子质量决定覆盖
3. 对未修复漏洞"顺手深挖"——法律红线，披露流程才是护身符
4. 复现环境乱堆——目录规范+容器化，否则三个月后自己看不懂
5. 忽视"同类代码 grep"——漏洞常成族出现，这是效率密码

## ✅ 自测题

<details>
<summary>1. 为什么复现要先容器化？</summary>

可复现性+可抛弃性：环境依赖锁死在 compose 文件里，任何人（含未来的你）一键重建；用完即弃不污染宿主机。

</details>

<details>
<summary>2. 补丁 diff 里"新增白名单"透露什么？</summary>

原实现对输入来源做了信任假设；白名单枚举的值域往往就是攻击者可控面——按语义反推 PoC 输入空间。

</details>

<details>
<summary>3. Fuzzing 为什么找不到逻辑漏洞？</summary>

逻辑漏洞的"错误"不是内存/崩溃层面，而是"业务上不该允许"——没有可自动判定的 oracle，只有理解业务的人能判断。

</details>

<details>
<summary>4. 90 天披露窗口的意义？</summary>

给厂商合理修复时间的同时设定明确期限，防止无限拖延；对研究者是保护（协调披露=合法身份）。

</details>

<details>
<summary>5. "同类代码 grep"为什么是 1-day 捷径？</summary>

开发者常复制粘贴同一模式；一处漏洞的"模式签名"在代码库中往往多处存在，一处修复常漏同族。

</details>
